# Changelog

## 0.1.0 (unreleased)

The first version.

- One command, `bollplank`, in plain Node 20 or later with no dependencies. Every command prints one JSON result, except the setup commands, which talk to a person. `bollplank <command> --help` prints each command's usage.
- Setup: `install.sh` (with `--no-init` and `-- <init options>`), `bollplank init`, `doctor`, `update` and `uninstall`. Init finds Claude Code and Codex and their subscription sign in, reads Linear from each client, writes `~/.bollplank/config.json` and links the skills, in seven steps that an answers file can drive. It never creates a Linear status and never replaces a file or link it did not make. Doctor checks every kit skill in each client, Linear from each client found, and the configured team, projects and statuses against Linear. The Linear probes start with only Linear read tools, and Codex is probed only through Linear's MCP server, never a ChatGPT connector. `update --pre` takes pre-releases, and update never goes back. `uninstall --purge` refuses a folder that is not a Bollplank home and a held ship lock.
- One validated config with the approver, copy style, board team, project and statuses, critic setting, ship lock and projects. Relative paths resolve against the config's folder. `bollplank context` gives skills everything they need from it, including each project's board and its critic default. A project may set its own `critic.default`, and a `shipOrder` lists every repo once.
- The Workflow line `Bollplank <version>, build <n>` from `bollplank version`, on every brief and comment.
- The critic, `bollplank critic`, for Claude Code and Codex on subscriptions only. Model keys, provider routes and client session markers are removed from its environment. It gets no board, no MCP servers and no connectors with either client, and fails with `critic-used-tools` if a client gives it a tool anyway. The wrapper writes the critique's Reviewer, Model and Workflow lines, with the model the client reported. One session per ticket is reused across the brief, plan and code, with rounds counted per subject, one call at a time, and `--new-session` for a session the client lost.
- Same model mode: a separate session of the lead's own client with a harder prompt, used only when chosen, and labelled in the Reviewer line. Nothing switches the critic on its own.
- Eight skills: `bollplank-brief`, `-critique`, `-address`, `-approve`, `-run`, `-ship`, `-accept` and `-board`, with Linear as the only board.
- Ticket runs in three modes: repository, consulting and configuration. Runs are off unless a project sets `runs` to `true`.
- `bollplank ticket` for worktrees per repo with a base branch per repo, `bollplank run` for the run record and its review gates, `bollplank turn` for the shipping lock, which another kit writing the same record can share, and `bollplank merge`, which merges only on green configured checks and complete review stages, for the run's own ticket, repo and ticket branch PR, and with a selected code stage only when the PR head carries the change approved for that repo by verbatim patch id, which keeps whitespace. A code round names the reviewed head of each repo with `--revisions`, and `bollplank run check-shipped` says whether every changed repo is merged and deployed.
- `bollplank deploy-wait` with the deploy kinds `none`, `command`, `amplify` and `github-actions`, each returning a status of `succeeded`, `failed` or `timeout` and a ref that `bollplank run deploy` records.
- `bollplank ledger` for tokens per model and the timeline of each ticket, reading markers from both Bollplank and the kit it replaces.
- The gate `scripts/check.mjs`, run in CI on Ubuntu, macOS and Windows with Node 20 and 22, with a private name check whose list lives outside the repo. It reads whole messages, authors and committers, binary and `-diff` files and merge changes, and fails on a shallow clone or an invalid pattern. Projects can opt in to the same check at merge with `privateScan`, which also scans the PR title and body that become the squash message.
