# Parity

Bollplank replaces a private kit that ran the same workflow for one person's projects. This page maps every part of the private kit it replaces to its Bollplank equivalent, and names the tests in `test/` that prove the equivalent works. Every test uses synthetic names and fake programs.

Skills are instructions to a model, so no test runs them. The gate checks that every skill has valid frontmatter and a name starting with `bollplank-`, and the tests below cover the commands each skill relies on.

## Changes from the kit

These differences are deliberate.

- **The critic gets no board.** The private kit's critic read the issue from Linear itself, after a connectivity preflight. Bollplank's lead reads the board and puts the subject and its history in the prompt. The critic has no board tools, no MCP servers and no connectors, for either provider, and fails with `critic-used-tools` if a client gives it one anyway. The preflight and its failure code are gone.
- **Rounds per subject.** The private kit counted one series of rounds per ticket and critic. Bollplank counts brief, plan and code rounds separately in one reused session, and refuses a skipped or repeated round with `round-mismatch`.
- **No automatic critic switch.** The private kit always used the other model. Bollplank adds same model mode, used only when it is chosen in the config, in the brief or on the command line. A missing critic fails with `critic-unavailable` and never falls back.
- **No default model pin and no mismatch report.** The private kit pinned a default model for each critic and reported when another model ran. Bollplank pins nothing unless the config or the call does. The wrapper writes the critique's `Model:` line from the model the client reported, so the posted line shows what ran.
- **Claude Code on PATH first.** The private kit took the newest Claude Code bundled with the desktop app. Bollplank takes the `claude` on `PATH` first and the newest bundled copy only when there is none.
- **Base branch per repo.** The private kit assumed `master`. Bollplank uses each repo's `baseBranch`, else the remote's default branch, else `master`, in `ticket`, `merge` and `deploy-wait`.
- **Deploy kinds.** The private kit waited for Amplify jobs with fixed settings. Bollplank has `none`, `command`, `amplify` and `github-actions`, configured per repo, and ships repos in the project's `shipOrder`.
- **No infrastructure ship step by name.** The private kit's ship turn had a named step for infrastructure changes. Bollplank has none. A project that needs one describes it in its own ship procedure, which the ship skill follows inside the turn, or waits for it with a `command` deploy.
- **Shared ship lock.** `turn` writes the same holder record as the private kit's lock, so with `shipLock` pointed at its folder, a turn held by either kit blocks the other. A lock folder without a holder record is refused instead of crashing the release.
- **Both kits' ledger markers, but only Bollplank's critic bindings.** The ledger reads markers from `bollplank ledger mark` and from the private kit's `aw-ledger mark`, and lists any session that carries both. It does not read the private kit's critic bindings, so a ticket started on the private kit finishes there.
- **Both kits' skills answer similar words.** The private kit's skills and Bollplank's trigger on the same kind of request, such as "critique ACME-1". While both are installed, name Bollplank in the request, or use one session per kit.
- **Run eligibility is only `runs`.** The private kit allowed runs through a separate file with a list per ticket, and checked the project's profile for runs too. Bollplank allows runs per project with `runs` in the config, and nothing else.
- **The private name scan and `privateScan`.** Bollplank's own gate scans the whole history for a list of private names kept outside the repo, and fails when the list is missing. A project can opt in with `privateScan`, so `bollplank merge` runs the same scan on the PR head, scans the PR title and body, and writes the scanned text as the squash message. Projects without it merge as before.
- **A review check at merge.** With a selected code stage, `bollplank merge` compares the PR head with the approved revision by patch id and refuses a changed change with `review-stale`.
- **Version and build.** The private kit's version was bumped by hand and its build counted on `master`. Bollplank's Workflow line is `Bollplank <version>, build <n>`, where the version equals the release tag that `bollplank update` checks out, and the build is counted on the remote's default branch. Both still say when the copy has unmerged commits or local changes.

One smaller difference: settings live in `~/.bollplank/config.json`, outside the kit, instead of in the kit's own checkout.
